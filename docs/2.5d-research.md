# 2.5D staging: precedents, verified patterns and decisions

## Product target

Create original, human-like animations for presentations and videos: a small
flat character moves around a room with depth, jumps and points at an object.
Keyboard steering is a preview/authoring diagnostic, not a separate game product.
The working camera is angled orthographic/isometric; the user did not explicitly
select a camera. Default preview size is now 48 CSS pixels, with 40/48/64 choices.

The research distinguishes a documented mechanism from an inference about a
famous game's source code. We use no game artwork, sprite sheets, character
traces or proprietary assets.

## Directly verified engine patterns

### Separate the character from world geometry

[Godot's Sprite3D documentation](https://docs.godotengine.org/en/stable/classes/class_sprite3d.html)
explicitly describes a 2D texture in a 3D environment.
[SpriteBase3D](https://docs.godotengine.org/en/stable/classes/class_spritebase3d.html)
defines billboard, pixel-size, fixed-screen-size and depth-test controls.
The docs also warn that standard alpha blending can have overlapping-material
sorting issues. Turning depth testing off merely draws on top; it does not solve
correct world occlusion.

The [official Three.js Sprite implementation](https://github.com/mrdoob/three.js/blob/dev/src/objects/Sprite.js)
documents a camera-facing plane and explicitly states that sprites do not cast
shadows. A ground shadow therefore needs an explicit solution; a flat image
does not automatically gain believable world support by entering a 3D renderer.

### Define depth order deliberately

[Unity's official sorting manual](https://docs.unity3d.com/6000.0/Documentation/Manual/2d-renderer-sorting.html)
documents sorting layers, order within a layer, camera-distance behavior, and a
custom sort axis for top-down/isometric scenes. This supports explicit world/
camera ordering, not arbitrary DOM append order or screen-Y rules detached from
the chosen projection.

For our bounded original room, world X/Z and height Y are distinct. The
orthographic projection, floor support, collision footprints and depth key are
explicit. A simple painter's order handles original upright boxes and a paper
actor; it is not a general solution for intersecting transparent meshes.

## Renderer/framework comparison

| Option | Fit for presentation/video authoring | Concrete limitation / pivot gate |
|---|---|---|
| Current TypeScript rig + isometric SVG stage | Reuses deterministic poses, transparent DOM embedding, vector artifacts and existing SVG rasterization/video export. Original floor/box geometry and bounded depth ordering need no new runtime. | Complex overlapping/intersecting depth ranges can exceed painter's ordering. The stage must not claim arbitrary 3D geometry or lighting. |
| Three.js with flat characters in a 3D scene | Appropriate for real perspective cameras, richer meshes, depth-buffered opaque geometry and optional lighting. Explicit time sampling can still be deterministic at the pose level. | Adds a WebGL render/export path and texture/material/transparency handling. Sprite shadows and overlapping transparency still require care; a depth buffer is not a blanket transparency fix. |
| Godot Sprite3D / authored engine pipeline | Provides documented sprite-in-world controls, cameras and scene tools; useful if designer-driven room/scene authoring becomes primary. | Adds a separate authoring/build/export pipeline and integration work for the current TypeScript/MCP/vector workflow. It is not required merely because the room has depth. |

Pose determinism comes from explicit time/state evaluation, not from choosing
SVG instead of WebGL. Exact raster pixels can differ across platforms in either
path. Likewise, WebGL does not inherently require weakening CSP; runtime
bundling and actual deployment requirements must be evaluated specifically.

## Adopt now

1. Keep one original character/motion authority. World movement, projection
   and renderer choice must not create a second pose implementation.
2. Use real room X/Z floor coordinates and Y jump height. Camera projection
   happens after world support/contact planning.
3. Make the flat character readable and correctly occluded by the environment.
   Use a restrained floor shadow, clear near/far limbs and visible contacts.
4. Review at the actual 40/48/64-pixel size. Smaller is not automatically better:
   pose direction, hands, feet and target intention must remain readable.
5. Keep presentation/video choreography and deterministic preview/export primary.
   Keyboard control is a diagnostic and possible authoring aid, not a reason to
   add combat, camera navigation or a general game framework.

## Avoid

- Assuming every famous 2.5D title uses the same camera-facing mechanism.
- Copying game art or inferring engine internals from an unrelated interview.
- Using bloom/depth-of-field to disguise weak motion or blur tiny figure details.
- Treating a successful depth-sort test as evidence of natural human movement.
- Claiming a responsive controller simply because every key is recognized.

## Evidence-based pivot

The below-5 controller review already justified replacing whole-clip queuing
with explicit intent/contact-state planning using the shared solver.

Reconsider the room renderer if representative occlusion cases cannot be
resolved correctly with the bounded SVG stage, or if real perspective, complex
intersecting geometry or physically interacting lighting becomes required.
Prototype the same original room, actor and choreography in the alternative,
compare actual output/embedding/export, and record the keep/pivot decision.
Do not switch engines based solely on a famous project's visual label.
